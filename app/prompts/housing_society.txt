=== HOUSING SOCIETY — DOMAIN GLOSSARY & EXAMPLES ===

─────────────────────────────────────────────
SECTION A — QUERY INTENT GLOSSARY
─────────────────────────────────────────────

COMPLAINT / CASE STATUS:
"complaint" / "case" / "issue" / "problem" / "shikayat" / "report"
"meri complaint" / "mera case" / "status kya hai" / "kya hua"
"open complaints" / "pending cases" / "active issues"
"closed cases" / "resolved" / "band ho gaya"
→ cases table, JOIN users for complainant/assignee names

MY COMPLAINTS:
"meri complaints" / "mere cases" / "maine jo report ki" / "my issues"
→ cases WHERE complainant_id = <user_id>

ASSIGNED CASES (committee):
"mujhe assign kya" / "mere paas kya hai" / "my assigned cases"
"mujhe handle karna hai" / "my cases to resolve"
→ cases WHERE assigned_to_id = <user_id>

LOCATION QUERIES:
"wing A" / "B wing" / "parking" / "garden" / "gate" / "lobby"
"flat 404 ke paas" / "basement mein"
→ cases WHERE location ILIKE '%<location>%'

PRIORITY QUERIES:
"urgent" / "critical" / "high priority" / "emergency"
"low priority" / "medium" / "normal"
→ cases WHERE priority = '<priority>' (valid values: urgent, high, medium, low — NOT "critical", even though users may say that word; map it to priority='urgent')

─────────────────────────────────────────────
SECTION B — ACTION INTENT GLOSSARY
─────────────────────────────────────────────

REGISTER COMPLAINT:
"complaint register karo" / "case file karo" / "report karo"
"shikayat darz karo" / "new complaint" / "issue report karo"
→ register_complaint workflow → INSERT into cases

EVERY CHANGE TO AN EXISTING CASE — ASSIGN, COMMENT, OR CLOSE:
There is ONE workflow for all three of these: assign_case. It is NOT three
separate workflows — add_case_comment and close_case are retired (inactive)
and must never be used as an intent_key. assign_case takes a required
`action` field (enum: "assign" | "comment" | "close") that decides which of
the three actually happens:

  "assign karo" / "de do" / "handle karne do" / "<name> ko assign karo"
  "<committee member> ko case do" / "transfer karo"
  → assign_case, action="assign" → UPDATE cases SET assigned_to_id

  "comment daalo" / "note likho" / "update daalo" / "add note"
  "kuch likho case mein" / "remarks daalo"
  → assign_case, action="comment" → INSERT into case_activity
    (activity_type='comment', payload={"text": "<note text>"})

  "case band karo" / "close karo" / "resolve mark karo"
  "solved ho gaya" / "issue fix ho gaya" / "close the case"
  → assign_case, action="close" → UPDATE cases SET status='closed', closed_at=now()
    (MANDATORY: comment_text must be collected before confirming a close —
    see entity_schema's required_if on comment_text)

CRITICAL: `action` must be set via update_draft in the SAME turn it becomes
clear from the user's wording — do not leave it for a later clarification
round. If it is genuinely ambiguous, ask once with the three options, and
when the user answers, resolve their answer to the correct action value and
call update_draft with it immediately — do not re-ask the same question.

SECTION C — STATUS VALUES
─────────────────────────────────────────────

Case status flow: reported → under_review → action_taken → closed
Priority levels: urgent, high, medium, low

When user says:
"naya" / "fresh" / "abhi report hua" → status = 'reported'
"dekh rahe hain" / "under review" / "investigating" → status = 'under_review'
"kuch kiya gaya" / "action liya" → status = 'action_taken'
"band" / "closed" / "resolved" / "fixed" → status = 'closed'

SECTION E — QUERY EXAMPLES
─────────────────────────────────────────────

"wing B mein stray dog ka complaint karo"
→ register_complaint: title='Stray dog in Wing B', location='Wing B'
  (there is no separate animal_type field — fold the animal into the title)

"meri open complaints dikhao"
→ SELECT cc.*, u.name as complainant_name FROM cases cc
  JOIN users u ON u.id = cc.complainant_id
  WHERE cc.org_id=$1 AND cc.complainant_id=$2 AND cc.status != 'closed'
  ORDER BY cc.created_at DESC

"CS-26-08-00001 ka status kya hai"
→ SELECT cc.*, c1.name as complainant_name, c2.name as assigned_name
  FROM cases cc
  LEFT JOIN users c1 ON c1.id = cc.complainant_id
  LEFT JOIN users c2 ON c2.id = cc.assigned_to_id
  WHERE cc.org_id=$1 AND cc.case_number=$2

"kitne urgent cases open hain"
→ SELECT COUNT(*) FROM cases
  WHERE org_id=$1 AND priority='urgent' AND status != 'closed'

"Ravi ko CS-26-08-00003 assign karo"
→ assign_case: action='assign', case_number='CS-26-08-00003', assignee_name='Ravi'

"CS-26-08-00002 close karo — issue resolved"
→ assign_case: action='close', case_number='CS-26-08-00002',
  comment_text=<ask the user what was done to resolve it — mandatory, do not
  accept "resolved"/"fixed"/"done" itself as the note>

─────────────────────────────────────────────
SECTION F — CASE NUMBER FORMAT
─────────────────────────────────────────────

Format: CS-YY-MM-NNNNN, e.g. CS-26-08-00001 (August 2026, first case that month).

This is fully AUTO-GENERATED by the system when a complaint is registered —
it is a `computed` field in register_complaint's entity_schema. NEVER compute
or guess a case_number yourself, and NEVER write SQL to generate one; just
omit it from update_draft entirely when registering a new complaint. Only use
a case_number when the USER supplies one (to look up, assign, comment on, or
close an existing case) — accept whatever format they type (with or without
dashes/spaces); the system normalises it when matching.

─────────────────────────────────────────────
SECTION G — CASES SQL PATTERNS
─────────────────────────────────────────────

All cases for org with names:
SELECT cc.id, cc.case_number, cc.title, cc.status, cc.priority, cc.location,
       cc.created_at, cc.closed_at,
       u1.name as complainant_name,
       u2.name as assigned_name
FROM cases cc
LEFT JOIN users u1 ON u1.id = cc.complainant_id
LEFT JOIN users u2 ON u2.id = cc.assigned_to_id
WHERE cc.org_id = $1

With status filter:
... AND cc.status = $2

With priority filter:
... AND cc.priority = $2

Open cases (not closed):
... AND cc.status != 'closed'
ORDER BY CASE cc.priority
  WHEN 'urgent' THEN 1
  WHEN 'high' THEN 2
  WHEN 'medium' THEN 3
  WHEN 'low' THEN 4
END, cc.created_at ASC

COUNT by status:
SELECT status, COUNT(*) FROM cases
WHERE org_id=$1 GROUP BY status ORDER BY status

COUNT by priority (open only):
SELECT priority, COUNT(*) FROM cases
WHERE org_id=$1 AND status != 'closed' GROUP BY priority

─────────────────────────────────────────────
SECTION H — SLA / OVERDUE QUERIES
─────────────────────────────────────────────

Note: cases have no category/subcategory classification — register_complaint
only collects title, location, and priority. Do not reference categories or
subcategories anywhere; they are not part of this workflow.

"overdue cases" / "SLA breach" / "due limit exceeded" / "pending too long"
→ SELECT cc.case_number, cc.title, cc.priority, cc.due_date,
         u2.name as assigned_name
  FROM cases cc
  LEFT JOIN users u2 ON u2.id = cc.assigned_to_id
  WHERE cc.org_id = $1 AND cc.due_date < now() AND cc.status != 'closed'
  ORDER BY cc.due_date ASC

"cases due soon" / "SLA at risk"
→ SELECT cc.case_number, cc.title, cc.priority, cc.due_date,
         u2.name as assigned_name
  FROM cases cc
  JOIN priority_tat_rules ptr ON ptr.org_id = cc.org_id AND ptr.priority = cc.priority
  LEFT JOIN users u2 ON u2.id = cc.assigned_to_id
  WHERE cc.org_id = $1 AND cc.status != 'closed'
    AND cc.due_date BETWEEN now() AND now() + (ptr.reminder_threshold_minutes || ' minutes')::interval
  ORDER BY cc.due_date ASC
  -- "at risk" window is per-priority (priority_tat_rules.reminder_threshold_minutes),
  -- NOT a flat hardcoded window — matches app/scheduler/jobs.py's reminder logic.

RESPONSE TEMPLATE ADDITION — SLA-aware case status:
"*Case #{case_number}*
📋 {title}
⚡ Priority: {priority}
📊 Status: {status}
⏰ Due by: {due_date} {overdue_flag}
👤 Reported by: {complainant_name}
👷 Assigned to: {assigned_name}"

Where {overdue_flag} = "🔴 *OVERDUE*" if due_date < now() and status != 'closed', else blank.
