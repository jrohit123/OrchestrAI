The admin wants to add a workflow. Generate a COMPLETE structured workflow record as JSON.

ADMIN DESCRIPTION:
{description_block}

DATABASE SCHEMA (available tables):
{schema_text}

===RULES===
══════════════════════════ RULES ══════════════════════════════════

RULE 1 — workflow_type: read or action. When uncertain, prefer "read".

RULE 2 — training_phrases: 8-12 realistic WhatsApp-style phrases, English + Hinglish.
  Use {slot_name} for entity placeholders.

RULE 3 — entity_schema: Only entities actually needed. Per field:
  table, column, match (ILIKE/exact), required, format (wildcard/exact), type (string/integer/float)
  CRITICAL: Mark computed fields with "computed": true — these are NEVER collected from the user.
  For items arrays, include item_schema with per-item field definitions.
  Example for an invoice with computed GST:
  {
    "customer_name": {"type":"string","required":true,"table":"customers","column":"name","match":"ILIKE","format":"wildcard"},
    "items": {
      "type":"array","required":true,
      "item_schema": {
        "description": {"type":"string","required":true},
        "qty":         {"type":"integer","required":true},
        "unit_price":  {"type":"float","required":true},
        "gst":         {"type":"float","required":false,"computed":true},
        "total":       {"type":"float","required":false,"computed":true}
      }
    },
    "total_amount": {"type":"float","required":false,"computed":true}
  }
  RULE: Every field produced by calc_rules MUST appear in entity_schema with "computed":true.
  RULE: Never mark a computed field as "required":true — the user never provides it.

  ENUM COLUMNS — CRITICAL, this prevents live insert/update failures:
  When the schema shows a column with "(options: a, b, c)" (a real DB
  CHECK-constraint enum), the field mapped to that column MUST include an
  "enum" array with EXACTLY those values, e.g.:
    "residential_status": {"type":"string","required":true,"table":"residents",
      "column":"residential_status","match":"exact","enum":["first_owner","second_owner","tenant"]}
  This is not optional decoration — the runtime chat agent uses "enum" to
  capture the correct canonical value from whatever the user actually typed
  ("he's the first owner", "1st owner", etc.) instead of writing their literal
  phrasing straight into an insert/update, which otherwise crashes against the
  DB's real constraint with no way for the user to self-correct. Use
  "match":"exact" (not "ILIKE"/"wildcard") for enum fields — partial/fuzzy
  matching makes no sense against a fixed, small set of exact values.

RULE 4 — sql_template: Full parameterized SELECT for read workflows ($1=org_id, $2+ for entities).
  null for action workflows.
  This query is what actually RUNS in production every time someone uses this
  workflow — it is not a hint or an example, treat it with the same care as
  a query a senior engineer would ship. Two things make that possible:

  a) SELF-SCOPED WORKFLOWS ("my own X", "complaints I filed", "cases assigned
     to me", anything whose whole point is filtering to the person asking):
     use the literal sentinel value "$current_user" in sql_params_order at
     the position of that filter — NOT a real column value, NOT a field name
     from entity_schema. The runtime resolves "$current_user" to the actual
     requesting user's own ID automatically. Do not invent an entity_schema
     field for "who's asking" and do not try to join on a name — there is no
     reliable name value available at query time, only this sentinel.
     Example: "...WHERE cc.complainant_id = $2" with sql_params_order =
     ["$current_user"].

  b) OPTIONAL FILTERS (any entity_schema field feeding a param that is NOT
     required — the user might or might not mention it): write the WHERE
     clause so a NULL param means "don't filter on this," not "match
     nothing." Pattern: "AND ($3::text IS NULL OR case_number = $3)" —
     never a bare "AND case_number = $3", which returns zero rows the
     instant that filter isn't supplied. Required fields don't need this —
     only ones where the user might reasonably omit the filter.

RULE 5 — sql_params_order: entity_schema keys in $2,$3... order, OR the literal
  sentinel "$current_user" wherever RULE 4(a) applies. [] for action workflows.

RULE 6 — response_format: "table" (short uniform list) or "generic" (default JSON-style
  formatting — use for everything else). null for action workflows.

RULE 7 — business_glossary: 3-6 term mappings for this specific workflow.

RULE 8 — llm_system_prompt: Under 300 words. What it does, tables involved, 3 example inputs,
  1 disambiguation rule. Include the exact intent_key so the agent knows which workflow to use.

RULE 9 — adapter_method: "generic" for all workflows (execution is driven by steps[]).

RULE 10 — intent_key: unique snake_case derived from the workflow purpose.
  Use descriptive verbs (create, generate, update, get, set, delete) followed by the object.
  Examples: create_complaint, generate_invoice, update_order_status, get_customer_dues.
  Keep it short, clear, and domain-agnostic.

RULE 11 — pdf_config: doc_type, title_template, aging_analysis, show_key_insights, insight_focus.
  For action workflows also add theme and render_instructions (RULE 15).

RULE 12 — response_template: WhatsApp message after action. Use {variable} placeholders. null for reads.

RULE 13 — calc_rules (action workflows with computed fields):
  item_rules: per-line-item expressions using item fields + org columns.
  aggregate_rules: top-level expressions (e.g. sum of items).
  Available functions: round(x,n), abs(x), min(a,b), max(a,b), sum_field(items,'field'), count_field(items).
  CRITICAL: Every field produced here MUST have "computed":true in entity_schema.
  CRITICAL: NEVER hardcode a tax/rate/fee value as a literal decimal (0.03, 0.1) —
  ALWAYS reference the actual column name for it, exactly as it appears in the
  DATABASE SCHEMA block above (the orgs table's own columns, injected fresh
  every time this prompt runs). Do not assume any particular org has a column
  called "gst_rate" or any other fixed name — read whatever rate/tax/fee column
  the live schema actually shows for THIS org, and use that name. If this org's
  orgs table has no such column at all, the workflow has nothing to compute a
  rate from — leave the fee/tax out of calc_rules rather than inventing a
  column or a hardcoded percentage.
  Example shape only — substitute the real column name from schema_text, this
  is not a fixed name to reuse verbatim:
  {
    "item_rules": {
      "tax":   "round(unit_price * qty * <org's actual rate column> / 100, 2)",
      "total": "round(unit_price * qty + tax, 2)"
    },
    "aggregate_rules": {
      "total_amount": "round(sum_field(items, 'total'), 2)"
    }
  }
  {} for read workflows.

RULE 14 — steps (action workflows — this IS the execution logic):
  Ordered array of {"op":"...", "params":{...}}.
  Available ops:
    resolve_entity  — {"table","name_from":"$fields.X","into":"alias","match_column":"name"}
                      optional: "expose":{"ctx_alias":"db_column"} to copy row values into fields
                      COMPOSITE KEY LOOKUP: if no single column uniquely identifies the row
                      (e.g. a flat is only unique by wing + flat number together — flat
                      numbers commonly repeat across different wings/towers), use
                      "match_columns":{"col1":"$fields.x","col2":"$fields.y"} instead of
                      match_column/name_from — this ANDs a match across every listed column
                      in ONE resolve_entity step. NEVER emit two separate resolve_entity
                      steps into the same "into" alias to fake a multi-column match — the
                      second one silently overwrites the first's result, so whichever
                      column that second call matched on ends up being the ONLY thing
                      actually filtered on, silently dropping the other column entirely.
    compute         — {} — REQUIRED whenever calc_rules is non-empty
    otp_gate        — {"amount_field":"$computed.total_amount"}
    approval_gate   — {"amount_field":"$computed.total_amount"}
    db.insert_row   — {"table","values":{"col":"$fields.X|$computed.X|$alias.id|$org_id|$user.user_id|literal"},
                       "sequence":{"field":"doc_number_col","prefix":"INV-","start":100}}
    db.update_row   — {"table","set":{"col":"$fields.X|NOW()"},"where":{"col":"$alias.id"}}
    db.upsert_row   — {"table","values":{...},"conflict_columns":["col1","col2"]}
    pdf.generate    — {"subtitle":""}
    notify.whatsapp — {"attach_pdf":true}

  CRITICAL DB INSERT RULES:
  - status values MUST be lowercase: "pending" NOT "PENDING", "sent" NOT "SENT"
  - For due dates use the special literal "TODAY+30" (30 days from today) or "TODAY"
    NEVER use SQL expressions like "NOW() + INTERVAL '30 days'" — they don't work as string literals
  - Never include columns that have DB defaults (created_at, updated_at) — let the DB handle them

  Example invoice insert:
  {"op":"db.insert_row","params":{"table":"invoices","values":{
    "org_id":"$org_id","customer_id":"$customer.id","created_by":"$user.user_id",
    "items":"$fields.items","amount":"$computed.total_amount",
    "status":"pending","due_date":"TODAY+30"
  },"sequence":{"field":"invoice_number","prefix":"INV-","start":100}}}

  Typical pipeline for invoice/quotation:
    resolve_entity → compute → otp_gate → approval_gate → db.insert_row → pdf.generate → notify.whatsapp
  For status update: resolve_entity → db.update_row → notify.whatsapp
  [] for read workflows.

  CONDITIONAL STEPS — ONE WORKFLOW THAT DOES DIFFERENT THINGS PER ACTION VALUE:
  Any step may carry a "when" guard — the step only runs if the condition is
  true, otherwise it's skipped entirely. This is how a single workflow
  branches its behaviour off an enum field (e.g. an "action" field with
  values like "add"/"update_status", or "assign"/"comment"/"close") instead
  of needing a separate workflow per branch:
    {"op":"db.insert_row","when":{"field":"$fields.action","equals":"add"},"params":{...}}
    {"op":"resolve_entity","when":{"field":"$fields.action","equals":"update_status"},"params":{...}}
    {"op":"db.update_row","when":{"field":"$fields.action","equals":"update_status"},"params":{...}}
  Guard syntax (same shape as gates[].when): {"field":"$fields.X","equals":"..."},
  "not_equals", "in":[...], "not_in":[...], "exists":true/false, "gte"/"lte"/"gt"/"lt"
  for numbers, or {"and":[cond1,cond2]} to require several at once. A step with
  no "when" always runs.
  CRITICAL: whenever entity_schema has a field whose whole purpose is to pick
  between different behaviours (an action/type/mode enum), every step that
  should only happen for ONE of those values MUST carry a matching "when" —
  omitting it means that step runs unconditionally on every invocation
  regardless of which value was chosen, which for db.insert_row/db.update_row
  means silently doing the wrong database operation (e.g. inserting a
  duplicate row when the admin only meant to update an existing one).

RULE 15 — pdf_config theme + render_instructions (action workflows):
