Section 04

Request Lifecycle

What happens from the moment a user sends a WhatsApp message to the final reply. Every step is traceable, logged, and recoverable.

💬
1. Message Received
WhatsApp/Telegram webhook fires. Channel adapter normalises the message into a standard payload regardless of source.
POST /webhook/whatsapp → { channel: "whatsapp", from: "+919876543210", text: "Generate invoice for Rajan Corp ₹45000 10 units ring" }
🪪
2. Identity Resolution
Phone number looked up in users table. Org, role, and permissions fetched. Unknown users get an onboarding prompt.
SELECT u.*, r.permissions FROM users u JOIN roles r ON r.id = u.role_id WHERE u.phone = '+919876543210'
🛡️
3. Permission Gate
Pre-AI check: does this role have "create_invoice" in its permissions? If not, respond immediately without touching the AI engine — saves cost and latency.
if "create_invoice" not in user.permissions: return "You don't have access to this action."
🧠
4. Intent Parsing
LLM extracts structured intent from natural language. Returns action key + entities. Low-confidence intents trigger a clarifying question back to the user.
{ action: "create_invoice", entities: { customer: "Rajan Corp", amount: 45000, sku: "ring", quantity: 10 }, confidence: 0.97 }
📋
5. Workflow Config Loaded
Active workflow for this org + intent_key fetched from DB. Versioned — if admin updated config mid-day, new requests get new version instantly.
SELECT * FROM workflows WHERE org_id = $org AND intent_key = 'create_invoice' AND is_active = true
⚙️
6. Playbook Execution
Steps executed in sequence. Each step: resolve params → call adapter → evaluate condition → proceed or branch. Step results passed as context to next step via {{step_n.result}} tokens.
step1: check_stock → OK (42 available) → step2: get_customer → {gst, address} → step3: create_invoice → invoice #1042 → step4: deduct_stock → 32 remaining
📝
7. Audit Log Written
Every step outcome, adapter called, data touched, and final result written to audit_log. Immutable. Queryable by org admin.
✅
8. Response Sent
Composed natural language reply sent back to original channel. WhatsApp gets a concise message. Web gets a structured card with links.
"✅ Invoice #1042 raised for Rajan Corp — ₹45,000. Stock updated: 32 rings remaining. PDF: [link]"

Section 06

Security Design

Security is built into the architecture, not bolted on. Every layer has a distinct security responsibility. No single point of failure.

🔐
Zero-Trust by Default
Every request re-verified against live role permissions. No cached privilege escalation. Token expiry enforced.
JWT (15min) + refresh tokens
🏢
Tenant Isolation
Every DB query scoped by org_id. Row-level security enforced at PostgreSQL level as a second line of defence.
PostgreSQL RLS policies
🔑
Credential Encryption
Third-party API keys stored encrypted in DB using AES-256-GCM. Master key in environment variable, never in code.
AES-256-GCM + env secret
📵
Pre-AI Permission Gate
Out-of-scope requests rejected before the LLM sees them. Saves cost, prevents prompt injection via role bypass attempts.
FastAPI dependency middleware
📋
Immutable Audit Trail
audit_log rows are append-only. No UPDATE/DELETE allowed on this table. Admins can query but not edit.
PostgreSQL trigger + grants
🌐
Webhook Verification
All inbound webhooks verified via HMAC signature before processing. Replay attacks blocked by timestamp check.
HMAC-SHA256 + nonce
🚦
Rate Limiting
Per-user and per-org rate limits on message processing. Prevents abuse and runaway LLM cost.
Redis sliding window
🧹
Data Minimisation
LLM only receives the minimum context needed. PII stripped from AI prompts where not required for the action.
Prompt template design
